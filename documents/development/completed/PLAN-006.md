0. ЦЕЛЬ PLAN-006
   ==================================================

Переход состояния:

ИЗ:

Home — витрина маркетплейса («Новинки / Популярное / Бесплатные»).
Задняя половина return-петли работает (follow → notification → return,
PLAN-005), но передняя отсутствует: открыв сайт, пользователь не видит
жизни экосистемы. Все источники активности существуют как данные,
но нет ни одной поверхности, где они сходятся.

В:

Home — живой вход в экосистему. За первые 30 секунд пользователь
(включая Guest) видит, что происходит в MTA прямо сейчас: кто онлайн,
что вышло, что обсуждают — и от любого элемента может перейти к реальной
сущности (DAILY-EXPERIENCE §2, §3, §47).

После PLAN-006 человек должен иметь возможность:

открыть сайт без намерения что-либо купить
→ увидеть живой сигнал экосистемы
→ заметить высокоценное событие
→ перейти к серверу / ресурсу / обсуждению / отзыву
→ совершить meaningful action
→ получить причину вернуться.

Это реализует переднюю половину ultimate loop:

DISCOVER → INTERACT → (FOLLOW → NOTIFICATION → RETURN — уже работают)

1. СТРАТЕГИЧЕСКАЯ ИДЕЯ
   ==================================================

PLAN-006 не называется:

"Homepage redesign".

И:

"Activity feed".

Суть не в ленте и не в косметике.

Настоящая цель:

"Сделать экосистему видимой на главной поверхности платформы."

Все источники активности уже существуют как данные:

- серверы онлайн — Server + ServerStatusSample;
- новости и обновления серверов — ServerNews (PUBLISHED), ServerUpdate;
- обсуждения — ForumThread, ForumPost;
- ресурсы и версии — Resource (PUBLISHED), ResourceVersion;
- отзывы — ServerReview, Review;
- новые серверы — Server (VERIFIED/ACTIVE).

Чего нет — единого read-слоя и поверхности, где они сходятся.

PLAN-006 строит именно это. Не дублирует существующее.

3. АРХИТЕКТУРНОЕ ПРАВИЛО — НОВОГО ДОМЕНА НЕТ
   ============================================

Activity является derived read layer (DAILY-EXPERIENCE §17, §45).

Жёсткие правила:

1. НЕТ новой таблицы/сущности Activity как source of truth.
2. Источники истины остаются: Server, Resource, Forum, ServerNews,
   ServerUpdate, Review.
3. Activity вычисляется ограниченными запросами к существующим таблицам
   в фиксированном временном окне.
4. Каждый activity item ссылается на конкретную реальную сущность
   (id/slug + deep link).
5. Никаких ручных/админских "публикаций в активность". Активность либо
   производная от публичных фактов, либо её нет.

Аддитивные изменения схемы допускаются только:
- индексы под оконные запросы;
- одно поле User для «с момента последнего визита» (Workstream I).

4. WORKSTREAM A — ГРАНИЦЫ И ИССЛЕДОВАНИЕ
   ======================================

A-001 — Аудит перед разработкой

Проверить существующее:

- Server + ServerStatusSample (monitoring, showStats);
- ServerNews / ServerUpdate (статусы, публикация, обсуждения);
- Resource / ResourceVersion (публикация, релизы версий);
- ForumThread / ForumPost / server-linked threads (showCommunity);
- ServerReview / Review (видимость, модерация);
- /news, /community (activity), /resources/homepage, /search;
- dashboard /dashboard/community (My MTA виджеты);
- Redis-инфраструктура кэша и rate limits.

Не создавать второй источник там, где данные уже есть.

---

A-002 — Определение «высокоценного события»

Список событий, попадающих в активность, фиксируется явно (см. D-001).
Всё остальное шумом не является событием вовсе, а не «событием с низким
приоритетом» (DAILY-EXPERIENCE §40).

---

A-003 — Read-only boundary

Activity read-layer не пишет в домены. Никаких side effects на
существующие мутации (публикация новости не обязана «создавать запись
активности» — активность просто видит опубликованную новость).

=================================================
5. WORKSTREAM B — LIVE LAYER (ГЛОБАЛЬНЫЕ АГРЕГАТЫ)
   ================================================

B-001 — Live line

Публичные агрегаты из реальных данных:

- N игроков онлайн (сумма текущих playerCount по критериям B-002);
- M серверов онлайн;
- computedAt (время расчёта/кэша).

Формат — быстрый сигнал, не монитор (§4: «не превращать это в Twitch»).

---

B-002 — Правила подсчёта (честность)

В агрегат входят только серверы, которые:

- lifecycle = VERIFIED или ACTIVE;
- monitoring = ONLINE;
- showStats = true;
- имеют реальный playerCount из heartbeat.

Не входят:

- UNKNOWN («система не знает» ≠ «онлайн»);
- OFFLINE;
- SUSPENDED / ARCHIVED / PENDING;
- серверы с выключенной статистикой (privacy, PLAN-005 S/T).

Если данных нет — честный ноль/пусто. Никаких fake numbers
(VISION Principle 5, ARCHITECTURE §63).

---

B-003 — Кэш

Агрегат считается по bounded запросу и кэшируется в существующем Redis
с коротким TTL (порядка 30–60 секунд). Каждый request не пересчитывает
всё (§44).

---

B-004 — Деградация

При пустом кэше — один bounded запрос, а не лавина. При ошибке источника —
показать «нет данных», не выдумывать значение.

6. WORKSTREAM C — ACTIVITY READ-LAYER
   ===================================

C-001 — Единый read-модуль

Один серверный read-модуль (например, lib/activity + публичный GET
эндпоинт), отдающий смешанную ленту высокоценных событий. Home — его
первый потребитель.

---

C-002 — Временное окно

Фиксированное окно (по умолчанию 7 дней, максимум 30). События старше
окна не возвращаются. Окно — константа конфигурации, не запрос клиента.

---

C-003 — Bounded queries

По одному ограниченному запросу на источник (LIMIT, существующие или
добавленные индексы createdAt/publishedAt/lastPostAt). Слияние в памяти.
Никаких N+1, никаких сотен запросов, никаких полных сканов (§44).

---

C-004 — Кэш

Готовая страница активности кэшируется (Redis, короткий TTL). Кэш —
оптимизация, не источник истины.

---

C-005 — Пагинация

Фиксированный limit на страницу ленты. Честная пагинация (как в /news),
без «бесконечной» подгрузки на первом этапе.

---

C-006 — Форма item

Каждый item несёт:

- type (из D-001);
- createdAt (реальное время события);
- entity reference (id/slug);
- deep link destination;
- минимальный контекст для рендера (title/name, иконка-источник).

---

C-007 — Готовность к /activity

Форма ответа проектируется так, чтобы потенциальный маршрут /activity
(DAILY-EXPERIENCE §21) добавлялся позже той же лентой с большим окном,
без переделки слоя. В PLAN-006 маршрут /activity НЕ строится.

=================================================
7. WORKSTREAM D — ACTIVITY TYPES И РАНЖИРОВАНИЕ
   =============================================

D-001 — Минимальный набор типов (DAILY-EXPERIENCE §18)

В скоупе:

SERVER_ONLINE        — сервер перешёл в ONLINE (по реальным сэмплам)
SERVER_UPDATE        — опубликован ServerUpdate
SERVER_NEWS          — опубликована ServerNews
NEW_SERVER           — сервер стал VERIFIED/ACTIVE (видим в discovery)
RESOURCE_RELEASE     — ресурс опубликован (PUBLISHED)
RESOURCE_UPDATE      — вышла новая ResourceVersion
NEW_DISCUSSION       — создана тема форума
DISCUSSION_REPLY     — ответ в теме
NEW_REVIEW           — новый публичный отзыв (сервер или ресурс)

CREATOR_PUBLICATION и NEW_ARTICLE — ЗАРЕЗЕРВИРОВАНЫ, не генерируются:
статей/публикаций создателей ещё не существует (Content-фаза).
Десятки новых типов не вводить (§18).

---

D-002 — Что НЕ является событием

- реакции, просмотры, лайки («someone liked something» — §40);
- покупки и продажи (§41: приватное действие; агрегат «X продаж» остаётся
  метрикой карточки ресурса, но не событием ленты);
- регистрации пользователей;
- moderation-действия;
- сердцебиения (heartbeat — это данные мониторинга, не событие).

---

D-003 — SERVER_ONLINE derivation

SERVER_ONLINE выводится из реальных сэмплов (переход OFFLINE/UNKNOWN →
ONLINE в окне). Если вычисление по сэмплам слишком тяжёлое — допустимо
упрощение «сервер сейчас ONLINE и последняя смена статуса в окне».
Требование одно: никакой синтетики; в сомнительных случаях тип исключить,
а не подделать.

---

D-004 — Ранжирование

Chronological (свежие выше) + детерминированная приоритизация при
сопоставимой свежести (§19, §40):

SERVER_UPDATE / RESOURCE_RELEASE / NEW_SERVER / NEW_ARTICLE(позже)
выше, чем DISCUSSION_REPLY / NEW_REVIEW.

Без ML. Без «TikTok ranking». Без персонализации (§6: сначала только
реальная активность).

---

D-005 — Dedup

Одна сущность не должна заполнять ленту: не более ограниченного числа
items на одну сущность в странице (например, серия ответов в одной теме —
один item «тема: N новых ответов», а не 15 items).

8. WORKSTREAM E — ПРАВИЛА ПУБЛИЧНОСТИ ACTIVITY
   ============================================

Критический workstream (§41–42, MODEL §40, ARCHITECTURE §34).

E-001 — Только публичные факты

В активность попадают только события сущностей в публичном состоянии:

- ServerNews: только PUBLISHED;
- ServerUpdate: только опубликованные;
- Resource: только PUBLISHED; ResourceVersion: только released;
- ForumThread/ForumPost: только не удалённые/не скрытые;
- Review/ServerReview: только не скрытые модерацией;
- Server (NEW_SERVER, SERVER_ONLINE, live-агрегаты): только VERIFIED/ACTIVE.

---

E-002 — Черновики невидимы

Draft news/updates/drafts ресурсов не порождают activity. Никогда.

---

E-003 — Модерация применяется

Скрытые модерацией объекты (HIDDEN review, soft-deleted пост, suspended
сервер) исчезают из активности немедленно, как и из остальных публичных
поверхностей.

---

E-004 — Приватность owner-флагов уважается

- showStats=false → сервер не участвует в live-агрегатах и SERVER_ONLINE;
- showCommunity=false → server-linked темы этого сервера не порождают
  activity items (согласовано с PLAN-005 G-002).

---

E-005 — Социальный граф закрыт

Никогда не публиковать: кто что купил, кто на кого подписан, состав
followers, membership. Follower count остаётся агрегатом на странице
сервера, не событием ленты.

---

E-006 — Проверка на backend

Все правила E-001..E-004 enforced на уровне read-слоя (backend), а не
скрытием в UI. Проверяется тестами (§18).

9. WORKSTREAM F — HOME REBUILD
   ============================

F-001 — Целевая структура Home (DAILY-EXPERIENCE §3)

1. «СЕЙЧАС В MTA» — live line (B-001) + глобальный поиск;
2. «АКТИВНОСТЬ» — лента высокоценных событий (C/D);
3. «ПОПУЛЯРНОЕ» — Top Servers / Hot Discussions / Fresh Resources (H);
4. Ниже — существующие маркетплейс-секции (Новинки/Популярное/Бесплатные),
   сохранённые как блок «Маркетплейс».

Home должен быть живым и не перегруженным (§3). Ограниченное число items.

---

F-002 — Hero

Hero переориентируется с «магазина» на «жизнь»: live line prominent,
поиск, краткое позиционирование экосистемы. Текст «Ресурсы для твоего
сервера MTA:SA» переносится в маркетплейс-блок.

---

F-003 — Deep links

Каждый элемент Home (live line, item активности, popular-карточка) ведёт
на реальную сущность: /servers/[slug], /resources/[slug],
/community/forum/thread/[id], /news, профиль.

---

F-004 — «Смотреть всё»

Каждый блок имеет честный «Смотреть всё» в существующий раздел:
/servers, /community, /resources, /news. Маршруты не дублируются.

---

F-005 — Guest

Вся живая Home доступна Guest без регистрации (§29). CTA регистрации
появляется только там, где нужно действие (follow, отзыв, ответ).

---

F-006 — Регистрационный момент

Регистрация открывает действия (§30): follow → уведомления; Guest видит
ценность до регистрации («discover → value → register»).
